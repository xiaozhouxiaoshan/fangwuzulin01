本整理仅依据本地项目源码编写，不引用外部文献，因此本文档不含 DOI 或外部链接。代码片段保持项目原始实现逻辑，说明文字用于论文写作时的技术表述。若论文需要写“安全认证”“细粒度权限控制”或“生产级安全机制”，当前代码并不足以支撑这一结论，原因在于系统仍采用明文密码比对与基础 Token 校验。这一点应在论文中如实表述。

## 一、代码选取原则

论文正文不宜放入大段重复的增删改查模板。真正具有分析价值的代码，应当能够回答三个问题：系统如何识别用户身份，系统如何限制不同角色访问不同业务数据，系统如何把房源、预约和报修这些核心业务串联起来。基于这一标准，本项目最值得纳入论文的代码集中在五个位置：登录认证链路、角色菜单配置、房源分页与房主隔离、预约看房流程、房屋报修与文件上传。

如果论文篇幅有限，正文建议保留三组代码：认证拦截、房源查询、预约或报修流程。其余代码更适合作为附录。这样处理可以避免正文沦为接口清单，也能让论证集中在系统机制而不是模板生成痕迹。

## 二、身份认证与会话控制

这部分代码构成了系统的入口逻辑。用户在前端提交账号、密码与角色，后端校验账号信息后签发 Token，拦截器在后续请求中解析 Token 并把用户编号、角色名、数据表名写入 Session。论文若要说明“系统具备基本身份识别和会话维持能力”，这一组代码最具代表性。

### 2.1 后端登录接口

源码位置：`back/src/main/java/com/controller/YonghuController.java`

```java
@IgnoreAuth
@RequestMapping(value = "/login")
public R login(String username, String password, String captcha, HttpServletRequest request) {
    YonghuEntity user = yonghuService.selectOne(new EntityWrapper<YonghuEntity>().eq("yonghuming", username));
    if(user==null || !user.getMima().equals(password)) {
        return R.error("账号或密码不正确");
    }
    
    String token = tokenService.generateToken(user.getId(), username,"yonghu",  "用户" );
    return R.ok().put("token", token);
}
```

论文表述建议：

用户登录采用控制器直连业务服务的方式完成。接口先按用户名查询用户实体，再将输入密码与数据库字段进行一致性比对。校验通过后，系统调用 Token 服务生成令牌，并将该令牌返回前端。这个实现说明系统已经建立了“身份校验—令牌签发—前端持久化”的基本认证链路。需要诚实指出的是，该实现没有引入密码哈希与盐值处理，因此它适合被定义为课程设计或原型系统中的基础认证模块，而不宜表述为高安全级别认证方案。

### 2.2 Token 生成与失效时间控制

源码位置：`back/src/main/java/com/service/impl/TokenServiceImpl.java`

```java
@Override
public String generateToken(Long userid,String username, String tableName, String role) {
    TokenEntity tokenEntity = this.selectOne(new EntityWrapper<TokenEntity>().eq("userid", userid).eq("role", role));
    String token = CommonUtil.getRandomString(32);
    Calendar cal = Calendar.getInstance();   
    cal.setTime(new Date());   
    cal.add(Calendar.HOUR_OF_DAY, 1);
    if(tokenEntity!=null) {
        tokenEntity.setToken(token);
        tokenEntity.setExpiratedtime(cal.getTime());
        this.updateById(tokenEntity);
    } else {
        this.insert(new TokenEntity(userid,username, tableName, role, token, cal.getTime()));
    }
    return token;
}

@Override
public TokenEntity getTokenEntity(String token) {
    TokenEntity tokenEntity = this.selectOne(new EntityWrapper<TokenEntity>().eq("token", token));
    if(tokenEntity == null || tokenEntity.getExpiratedtime().getTime()<new Date().getTime()) {
        return null;
    }
    return tokenEntity;
}
```

论文表述建议：

令牌生成逻辑采用数据库持久化方案。系统生成长度为 32 的随机字符串，并设置一小时失效时间。当同一用户重复登录时，系统更新旧令牌及其过期时间，而不是继续累积多条无效记录。这个设计降低了会话管理复杂度，也为后续的拦截器校验提供了统一的数据来源。

论文表述建议：

## 五、预约看房流程

预约看房模块体现的是多角色共享同一业务表的处理方式。用户创建预约记录，房主审核预约请求，管理员可以统一查看。与其在论文里展示一个普通新增接口，不如展示分页时如何按角色切换查询条件。

源码位置：`back/src/main/java/com/controller/YuyuekanfangController.java`

论文表述建议：

预约看房的数据访问采用“同表多视角”的处理模式。控制器不为用户和房主分别维护两套查询接口，而是在统一入口中依据角色注入不同过滤条件。用户查看自己的预约记录时，条件字段是用户名；房主查看待处理预约时，条件字段切换为房主账号。这个实现降低了接口数量，也让预约流程保持了统一的数据结构。

### 6.2 文件上传与下载

源码位置：`back/src/main/java/com/controller/FileController.java`

```java
@RequestMapping("/upload")
public R upload(@RequestParam("file") MultipartFile file,String type) throws Exception {
    if (file.isEmpty()) {
        throw new EIException("上传文件不能为空");
    }
    String fileExt = file.getOriginalFilename().substring(file.getOriginalFilename().lastIndexOf(".")+1);
    File path = new File(ResourceUtils.getURL("classpath:static").getPath());
    if(!path.exists()) {
        path = new File("");
    }
    File upload = new File(path.getAbsolutePath(),"/upload/");
    if(!upload.exists()) {
        upload.mkdirs();
    }
    String fileName = new Date().getTime()+"."+fileExt;
    File dest = new File(upload.getAbsolutePath()+"/"+fileName);
    file.transferTo(dest);
    return R.ok().put("file", fileName);
}
```

论文表述建议：

系统采用服务器本地目录保存上传附件。接口先校验文件非空，再依据原始文件名提取扩展名，随后在静态资源目录下创建 `upload` 子目录并完成文件持久化。实现层面并不复杂，却支撑了报修图片、轮播图和其他媒体材料的统一上传流程。论文中可以把它描述为“基于 Spring MultipartFile 的本地文件存储实现”。

## 九、论文写作时必须如实说明的技术边界
